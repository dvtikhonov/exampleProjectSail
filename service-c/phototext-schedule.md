# PhotoText: фото графика производства → schedule через API VPS

Записать **график производства блюд** по **фото рукописного недельного графика**. OCR, маппинг дней недели на даты и вариации имён делает агент. Сервер принимает только канонические имена выбранного ресторана (точное `LOWER(name)`), а агент обрабатывает только явно указанные пользователем категории и пишет даты через `DishAvailabilityScheduleService::syncSchedule`. Fuzzy на сервере **нет**. Автосоздание отсутствующих блюд **нет**.

Код приложения **не менять**. Только HTTP к API. Токен в чат **не печатать**.

## Перед запуском

Пользователь **до** `/phototext-schedule` заполняет шапку и **прикладывает фото** рукописного графика (по дням недели). Текст после команды — тоже шапка, если поля ниже пустые.

```
BASE_URL=http://localhost:8083
Дата начала графика: ДД.ММ.ГГГГ
Ресторан: …
Категории: гарнир, Горячее
```

- **Дата начала графика** — любой день недели (не обязательно понедельник). Диапазон всегда **ровно 7 дней**: `date_from` … `date_from + 6` (`date_to`). Пример: `13.08.2026` (чт) → `2026-08-13` … `2026-08-19`.
- **Ресторан** — `id` или уникальное имя/подстрока активного ресторана (0 или >1 → STOP).
- **Категории** — обязательный список из 1+ категорий через запятую. Каждая категория должна однозначно сопоставляться с категорией каталога выбранного ресторана (по `id` или уникальному имени/подстроке). Агент обрабатывает и отправляет только блюда из этого списка. **График на сервере изменяется только по этим категориям** (остальные категории ресторана не трогать). В POST всегда передавать `category_ids` (массив id выбранных категорий); одиночный `category_id` допустим только если категория ровно одна.

Если нет `BASE_URL`/даты/ресторана/категорий или нет фото — **STOP**, попросить заполнить и приложить фото.

## Конфиг

```
BASE_URL=https://YOUR-VPS-HOST
```

Без завершающего `/`. Публичный URL VPS, куда nginx-gateway проксирует `/api/food/` в service-c (без Passport). Пример продакшена: `https://94-228-117-27.sslip.io`. Если пользователь указал другой `BASE_URL` в сообщении — взять его.

Для **локальной** работы в этом проекте по умолчанию использовать **прямой** `service-c`: `http://localhost:8083`.  
`http://localhost:8080` использовать только если пользователь явно просит проверить именно gateway-роутинг или если уже подтверждено, что `/api/food/phototext/*` на gateway доступен.

Токен: ключ `PHOTOTEXT_AGENT_TOKEN` из `service-c/.env`. Заголовок `X-PhotoText-Token`. Пустой токен — **STOP**. В логах и ответе пользователю токен не показывать.

Доступ к `/api/food/phototext/*` — **два** условия (middleware `phototext.agent.token` + `phototext.ai.access`):

1. Верный `X-PhotoText-Token`.
2. Активный AI-доступ у пользователя с ролью `max_manager` (`max_users.ai_access_until` > now). Включается кнопкой **«Вкл. доступ AI»** в админке mini-app (TTL **30 минут**). Одновременно активен только один доступ. Агент **не** включает доступ сам — только HTTP к PhotoText API.

Без активного AI-доступа (или если активный пользователь не `max_manager`) сервер отвечает `403` с `"message": "Доступ AI к базе не разрешён."` — **STOP**, попросить менеджера включить доступ AI и повторить команду.

HTTP выполнять **автоматически**, не перекладывая `curl` на пользователя. JSON — `Content-Type: application/json`.

Приоритет транспорта для HTTP:

1. Если Shell уже работает в Linux/WSL и команды возвращают нормальный `exit_code`, использовать обычный `curl`.
2. Если Shell работает через Windows PowerShell, **не** вызывать алиас `curl`/`Invoke-WebRequest`. Использовать `curl.exe`.
3. Если `BASE_URL` не указан и работа локальная, сначала пробовать `http://localhost:8083`.
4. Если пользователь указал локальный `BASE_URL`, но первый запрос `GET /restaurants` не дал валидный HTTP-ответ из-за транспорта/алиаса Shell, агент должен **сам** повторить запрос другим способом (`curl.exe` вместо `curl`, либо прямой `:8083` вместо gateway `:8080`, если это локальная среда).
5. Просить пользователя выполнить запросы вручную только если агент исчерпал оба автоматических варианта и не может получить ни одного HTTP-ответа.

## STOP (не угадывать, не слать apply)

Остановиться и сообщить причину, **без** `POST /schedule/apply`, если:

1. Нет даты начала, ресторана, списка категорий, `BASE_URL` (когда нужен) или фото.
2. `GET /restaurants`: 0 или больше одного совпадения с полем «Ресторан».
3. Хотя бы одна из указанных «Категорий» дала 0 или >1 совпадение в каталоге ресторана.
4. Не удалось однозначно сопоставить блюдо (0 или >1 кандидат в выбранном scope каталога по выбранным категориям).
5. Весь диапазон `date_from`…`date_to` в прошлом относительно `editable_from` (сегодня MSK) — сервер отвергнет; **STOP** до apply.
6. Сервер: `401` (токен); `403` (нет активного AI-доступа max_manager); пустой `matched` на apply (`422`); неверный span (`date_to ≠ date_from + 6`) → `422`.
7. После `POST /schedule/match` `matched_count` = 0.

Частичный матч (есть `matched` и `issues`) — `POST /schedule/apply` **тем же JSON** допустим: в график идут только matched.

## Поток

1. Разобрать шапку. Дату `ДД.ММ.ГГГГ` → `Y-m-d` (`13.08.2026` → `2026-08-13`). Построить окно: `date_from` = эта дата, `date_to` = `date_from + 6 дней`. Для каждого из 7 дней знать `Y-m-d` и день недели (Пн…Вс).
2. Определить рабочий URL/транспорт:
   - если `BASE_URL` не указан и работа локальная — взять `http://localhost:8083`;
   - если указан `http://localhost:8080`, помнить, что локально надёжнее прямой `service-c` на `http://localhost:8083`;
   - если первый HTTP-вызов сорвался на алиасе PowerShell или не дал понятный результат, автоматически переключиться на другой способ выполнения, а не останавливать сценарий сразу.
3. `GET {BASE_URL}/api/food/phototext/restaurants`  
   Заголовок `X-PhotoText-Token`.  
   - `401` — токен; **STOP**.  
   - `403` «Доступ AI к базе не разрешён.» — нет активного AI-доступа max_manager; **STOP**, попросить включить «Вкл. доступ AI» в админке и повторить.  
   Ответ при успехе: `{ "restaurants": [ { "id", "name" } ] }`.  
   Выбрать **ровно один** `restaurant_id`: числовое поле «Ресторан» = `id`; иначе уникальное имя (без учёта регистра, допускается уникальная подстрока). 0 или >1 — **STOP**.
4. `GET {BASE_URL}/api/food/phototext/catalog?restaurant_id={id}`  
   Дальше только этот каталог: `catalog.categories[]` (`id`, `name`, `dishes[].name`). Блюда из другого ресторана не использовать.  
   Поле «Категории» обязательно: выбрать **ровно по одному** совпадению для каждого элемента списка (по `id` или уникальному имени/подстроке среди категорий этого ресторана). Если хотя бы для одного элемента 0 или >1 совпадение — **STOP**. Собрать список `category_ids` выбранных категорий и **всегда** передавать его в match/apply (график меняется только в этом scope).
5. OCR фото рукописного графика:
   - распознать блоки `Понедельник`…`Воскресенье` (допускаются сокращения Пн/Вт/…/Вс);
   - пустой день / нет блока — нет позиций на эту дату;
   - сопоставить подпись дня с **конкретной датой внутри окна** `date_from`…`date_to` (не «первый Пн года»);
   - день с фото вне окна — в issues / не слать;
   - в каждый день — только имена блюд; зачёркнутое не брать;
   - агрегировать по блюду: одно имя в нескольких днях → `dates: [...]`.
6. Сопоставить названия с каталогом (см. ниже). Использовать только `dishes[].name` из выбранных категорий; блюда вне этих категорий игнорировать и не отправлять.
7. `POST {BASE_URL}/api/food/phototext/schedule/match` — сверка (график не пишется).
8. Если есть matched — `POST {BASE_URL}/api/food/phototext/schedule/apply` **тем же телом**.
9. Итог пользователю: ресторан, список обрабатываемых категорий, диапазон 7 дней, `applied`, позиции по дням, `issues`.

## Вариации имён (только каталог этого ресторана)

Сервер ищет точное имя (`LOWER(name)`). В POST — **каноническое** `dishes[].name` из каталога, не сырой OCR. Сервер сам определит `category_id` блюда.

1. Убрать вес (`100 г`), цену (`75 ₽`), лишние пробелы.
2. Искать только внутри явно указанных пользователем категорий. По всему каталогу ресторана не искать.
3. Сравнивать без учёта регистра, кавычек `«»""` и ё/е, если это даёт **ровно один** кандидат.
   Пример: «котлета домашняя» → «Котлета домашняя».
4. Допускается перестановка слов при том же наборе значимых токенов (без учёта регистра, кавычек, ё/е), если это даёт **ровно один** кандидат в выбранном scope.
   Пример: «домашняя котлета» → «Котлета домашняя». Не добавлять и не убирать значимые слова.
5. 0 или >1 кандидат (в т.ч. одно короткое имя в двух категориях) — эту строку **не угадывать**: не слать выдуманное имя, зафиксировать в отчёте (локально) и не включать в `entries`.
6. Не выдумывать блюда, которых нет в каталоге. Не создавать блюда через API.

## Тело match и apply

Одинаковый JSON:

```json
{
  "restaurant_id": 1,
  "category_ids": [3, 5],
  "date_from": "2026-08-13",
  "date_to": "2026-08-19",
  "entries": [
    { "name": "Салат «Колизей»", "dates": ["2026-08-13"] },
    { "name": "Салат \"Цезарь\"", "dates": ["2026-08-15"] }
  ]
}
```

Правила:

- `restaurant_id` — выбранный активный ресторан;
- `category_ids` — **обязателен** для агента: массив id категорий из шапки (1+). Альтернатива для одной категории — `category_id` (скаляр). Не передавать оба сразу. **Не опускать** scope: без категорий сервер заменит график по **всему** ресторану;
- `date_from` / `date_to` — `Y-m-d`, причём `date_to` = `date_from + 6` (ровно 7 дней);
- `entries` ≥ 1; `name` — каноническое имя каталога; `dates` — массив `Y-m-d` **внутри** диапазона.

Семантика apply на сервере:

- exact match по ресторану; при `category_ids` / `category_id` — только блюда этих категорий;
- данные с фото **однозначны**: ранее записанные даты в окне `date_from`…`date_to` в scope **удаляются** и заменяются содержимым фото;
- scope замены: **только** указанные категории; без scope — все категории ресторана (агенту запрещено);
- matched получают даты с фото; остальные блюда **указанного** scope в диапазоне получают пустой список дат (очистка); категории вне списка **не изменяются**;
- частичный матч допустим (как у orders): в график идут только matched, но очистка указанного scope полная.

## Ответы API

- `401` — токен; **STOP**.
- `403` — нет активного AI-доступа max_manager (`"Доступ AI к базе не разрешён."`); **STOP**, попросить включить доступ AI в админке.
- `GET /restaurants` — список `id`, `name`.
- `GET /catalog` — `{ "catalog": { "restaurant_id", "restaurant_name", "categories": [...] } }`.
- `POST /schedule/match` и `POST /schedule/apply`:

```json
{
  "matched_count": 12,
  "matched": [
    {
      "raw_title": "...",
      "dish_id": 742,
      "dish_name": "...",
      "category_id": 4,
      "category_name": "Супы",
      "dates": ["2026-08-13"]
    }
  ],
  "issues": [
    { "code": "dish_not_found", "message": "...", "raw_title": "...", "dates": ["..."] }
  ],
  "date_from": "2026-08-13",
  "date_to": "2026-08-19",
  "applied": true,
  "categories_applied": [4]
}
```

- `POST /schedule/match` → `applied: false`, `categories_applied: []`.
- `POST /schedule/apply` успех — `200`, `applied: true`. Пустой matched — `422`, график не пишется.
- Доменные ошибки дат/категории — `422` + `message`. Неверный span (`date_to ≠ date_from + 6`) → `422`.
- Коды `issues[].code`: `dish_not_found` \| `dish_ambiguous`.

## Итог пользователю

Кратко:

1. Ресторан: `id` + имя; список обрабатываемых категорий из шапки и категории matched.
2. Диапазон `Y-m-d` (**7 дней** с даты начала).
3. `applied: true/false` или причина STOP.
4. Позиции по дням (канонические имена + категория).
5. `issues` (нет в БД / неоднозначно) и строки, которые агент не отправил (0/>1 кандидат).

Не выкладывать токен и сырой `.env`.
