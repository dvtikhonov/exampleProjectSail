# PhotoText: фото бланка → заказ через API VPS

Оформить ручной заказ по **фото бланка**. OCR, вариации имён и разрез комбо делает агент. Сервер принимает только канонические имена выбранного ресторана (точное `LOWER(name)`), проверяет принадлежность блюд ресторану и пары `combo_ref`. Fuzzy и split по `/` на сервере **нет**.

Код приложения **не менять**. Только HTTP к API. Токен в чат **не печатать**.

## Перед запуском

Пользователь **до** `/phototext-order` заполняет шапку и **прикладывает фото** бланка. Текст после команды — тоже шапка, если поля ниже пустые.

```
Клиент:
Дата заказа: ДД.ММ.ГГГГ
Ресторан:
```

- **Клиент** — подстрока имени клиента MAX (`customer_query`), например `Сибирь-Финанс`.
- **Дата заказа** — дата доставки из шапки промпта. Дату в шапке бланка («Меню на …») **не читать и не использовать**.
- **Ресторан** — `id` или уникальное имя активного ресторана.

Если шапка неполная или нет фото — **STOP**, попросить заполнить и приложить фото.

## Конфиг

```
BASE_URL=https://YOUR-VPS-HOST
```

Без завершающего `/`. Публичный URL VPS, куда nginx-gateway проксирует `/api/food/` в service-c (без Passport). Пример продакшена: `https://94-228-117-27.sslip.io`. Если пользователь указал другой `BASE_URL` в сообщении — взять его.

Для **локальной** работы в этом проекте по умолчанию использовать **прямой** `service-c`: `http://localhost:8083`.  
`http://localhost:8080` использовать только если пользователь явно просит проверить именно gateway-роутинг или если уже подтверждено, что `/api/food/phototext/*` на gateway доступен.

Токен: ключ `PHOTOTEXT_AGENT_TOKEN` из `service-c/.env`. Заголовок `X-PhotoText-Token`. Пустой токен — **STOP**. В логах и ответе пользователю токен не показывать.

Доступ к `/api/food/phototext/*` — **два** условия (middleware `phototext.agent.token` + `phototext.ai.access`):

1. Верный `X-PhotoText-Token`.
2. Активный AI-доступ у пользователя с ролью `max_manager` (`max_users.ai_access_until` > now). Включается кнопкой **«Вкл. доступ AI»** в админке mini-app (TTL **30 минут**). Одновременно активен только один доступ. Агент **не** включает доступ сам — только HTTP к PhotoText API.

Без активного AI-доступа (или если активный пользователь не `max_manager`) сервер отвечает `403` с `"message": "Доступ AI к базе не разрешён."` — **STOP**, попросить менеджера включить доступ AI и повторить команду.

HTTP выполнять **автоматически**, не перекладывая `curl` на пользователя. JSON — `Content-Type: application/json`.

Приоритет транспорта для HTTP:

1. Если Shell уже работает в Linux/WSL и команды возвращают нормальный `exit_code`, использовать обычный `curl`.
2. Если Shell работает через Windows PowerShell, **не** вызывать алиас `curl`/`Invoke-WebRequest`. Использовать `curl.exe`.
3. Если `BASE_URL` не указан и работа локальная, сначала пробовать `http://localhost:8083`.
4. Если пользователь указал локальный `BASE_URL`, но первый запрос `GET /restaurants` не дал валидный HTTP-ответ из-за транспорта/алиаса Shell, агент должен **сам** повторить запрос другим способом (`curl.exe` вместо `curl`, либо прямой `:8083` вместо gateway `:8080`, если это локальная среда).
5. Просить пользователя выполнить запросы вручную только если агент исчерпал оба автоматических варианта и не может получить ни одного HTTP-ответа.

## STOP (не угадывать, не слать заказ)

Остановиться и сообщить причину, **без** `POST /orders`, если:

1. Нет клиента, даты, ресторана или фото.
2. `GET /restaurants`: 0 или больше одного совпадения с полем «Ресторан».
3. Не удалось однозначно сопоставить блюдо (0 или >1 кандидат в каталоге этого ресторана).
4. Сервер: клиент 0 или >1; `401` (токен); `403` (нет активного AI-доступа max_manager); пустой `matched` (`422`).
5. После `POST /match` `matched_count` = 0.

Частичный матч (есть `matched` и `issues`) — `POST /orders` **тем же JSON** допустим: в заказ идут только matched.

## Поток

1. Разобрать шапку. Дату `ДД.ММ.ГГГГ` → `Y-m-d` (`17.08.2026` → `2026-08-17`).
2. Определить рабочий URL/транспорт:
   - если `BASE_URL` не указан и работа локальная — взять `http://localhost:8083`;
   - если указан `http://localhost:8080`, помнить, что локально надёжнее прямой `service-c` на `http://localhost:8083`;
   - если первый HTTP-вызов сорвался на алиасе PowerShell или не дал понятный результат, автоматически переключиться на другой способ выполнения, а не останавливать сценарий сразу.
3. `GET {BASE_URL}/api/food/phototext/restaurants`  
   Заголовок `X-PhotoText-Token`.  
   - `401` — токен; **STOP**.  
   - `403` «Доступ AI к базе не разрешён.» — нет активного AI-доступа max_manager; **STOP**, попросить включить «Вкл. доступ AI» в админке и повторить.  
   Ответ при успехе: `{ "restaurants": [ { "id", "name" } ] }`.  
   Выбрать **ровно один** `restaurant_id`: числовое поле «Ресторан» = `id`; иначе уникальное имя (без учёта регистра, допускается уникальная подстрока). 0 или >1 — **STOP**.
4. `GET {BASE_URL}/api/food/phototext/catalog?restaurant_id={id}`  
   Дальше только этот каталог: `catalog.categories[]` (`name`, `is_combo_available`, `dishes[].name`). Блюда из другого ресторана не использовать.
5. OCR фото. В JSON — только позиции с **qty > 0**. Прочерки (`—`, `-`, пусто), состав, вес, цены, итог **не отправлять**.
6. Сопоставить названия с каталогом (см. ниже). Комбо со слэшем разрезать на две канонические позиции.
7. `POST {BASE_URL}/api/food/phototext/match` — сверка.
8. Если есть matched — `POST {BASE_URL}/api/food/phototext/orders` **тем же телом**.
9. Итог пользователю: `order_id`, позиции, `issues`.

## Вариации имён (только каталог этого ресторана)

Сервер ищет точное имя (`LOWER(name)`). В POST — **каноническое** `dishes[].name` из каталога, не сырой OCR.

1. Убрать вес (`100 г`), цену (`75 ₽`), лишние пробелы.
2. Обычная позиция: сначала категория бланка/каталога → внутри неё ровно одно блюдо. Пример: `Фасолька` → `Салат "Фасолька"`.
3. Сравнивать без учёта регистра, кавычек `«»""` и ё/е, если это даёт **ровно один** кандидат.
   Пример: «котлета домашняя» → «Котлета домашняя».
4. Допускается перестановка слов при том же наборе значимых токенов (без учёта регистра, кавычек, ё/е), если это даёт **ровно один** кандидат.
   Пример: «домашняя котлета» → «Котлета домашняя». Не добавлять и не убирать значимые слова.
5. 0 или >1 кандидат — эту строку **не угадывать**: не слать выдуманное имя, зафиксировать в отчёте (локально) и не включать в `items`.
6. Не выдумывать блюда, которых нет в каталоге.

## Разрез комбо

Строка вида `основное / гарнир` (слэш между двумя блюдами) — это **две** позиции, не одна.

- Два блюда из **разных** категорий с `is_combo_available: true` (горячее + гарнир).
- Одинаковый `quantity`.
- Общий `combo_ref` — новый UUID v4 на каждую пару. Разные комбо-строки — разные UUID.
- В JSON **нет** строки со слэшем. Не слать `"Филе минтая с овощами / Гречка"` одним `name`.
- Каждая половина — каноническое имя из каталога. 0 или >1 кандидат на половину — пару не слать.
- Прочерк в qty у комбо-строки — всю пару пропустить.

Сервер: один `combo_ref` — ровно две позиции, одинаковый qty; иначе `combo_unresolved`, обе строки не в заказ. Неполная пара не отправлять.

## Тело match и orders

Одинаковый JSON, без цен:

```json
{
  "customer_query": "Сибирь-Финанс",
  "order_date": "2026-08-17",
  "restaurant_id": 1,
  "items": [
    { "name": "Салат \"Фасолька\"", "quantity": 2 },
    { "name": "Филе минтая с овощами", "quantity": 1, "combo_ref": "11111111-1111-1111-1111-111111111111" },
    { "name": "Гречка", "quantity": 1, "combo_ref": "11111111-1111-1111-1111-111111111111" }
  ]
}
```

Правила: `customer_query` обязателен; `order_date` = `Y-m-d` из шапки; `restaurant_id` — выбранный активный ресторан; `items` ≥ 1; `name` — каноническое имя каталога; `quantity` 1–99; `combo_ref` — опциональный UUID.

Пример после OCR (не сырой бланк):

- `Салат "Фасолька"` × 2
- `Салат "Колизей"` × 1
- `Филе минтая с овощами` × 1 + `Гречка` × 1 (`combo_ref` A)
- `Филе минтая с овощами` × 2 + `Картофельное пюре` × 2 (`combo_ref` B)
- `Куриное филе, запечённое с помидором и сыром` × 1 + `Картофельное пюре` × 1 (`combo_ref` C)

Строки с qty «—» (помидоры, котлеты и т.п.) не входят в `items`.

## Ответы API

- `401` — токен; **STOP**.
- `403` — нет активного AI-доступа max_manager (`"Доступ AI к базе не разрешён."`); **STOP**, попросить включить доступ AI в админке.
- `GET /restaurants` — список `id`, `name`.
- `GET /catalog` — `{ "catalog": { "restaurant_id", "restaurant_name", "categories": [...] } }`.
- `POST /match` и `POST /orders`: `matched_count`, `matched[]` (`dish_name`, `quantity`, `combo_ref`, …), `issues[]` (`code`: `dish_not_found` | `dish_ambiguous` | `combo_unresolved`), `order_id`.
- `POST /orders` успех — `201` и `order_id`. Пустой matched — `422`, заказа нет.
- Ошибка клиента 0/>1 — сообщение сервера; **STOP**.

## Итог пользователю

Кратко:

1. Ресторан: `id` + имя.
2. Дата заказа (`Y-m-d`) из шапки.
3. `order_id` или причина, почему заказ не создан.
4. Позиции в заказе (канонические имена, qty, комбо-пары).
5. `issues` и строки, которые агент не отправил (0/>1 кандидат).

Не повторять цены и итог с бланка. Не выкладывать токен и сырой `.env`.
